# 下一批功能候选说明（五选二）

> 状态：讨论稿，不含实现。
> 读者：产品/营养师/开发都能看。每节先给“一句话结论”，再展开技术取舍。
> 共同前提：`coachApi / getFeed / advice / saveLog` 已部署到正式环境；拳王与营养师已绑定；至少有 14 天日志。未满足时，下面多数功能只能看到“数据不足”。

## 一页结论

| 排序 | 功能 | 一句话结论 | 工作量 |
|---|---|---|---|
| 1 | 官方称重对比 | 数据模型早就有、界面还没接，补上就能把“官方称重 vs 日常晨重”讲清楚，最便宜 | 小 |
| 2 | 节奏红线看板 | 把已经存下来的告警和体重速率汇总成一张教练总览，提前发现“掉太快/缺口太深” | 中 |
| 3 | 教练端批量待办 | 一次处理多条待办，省教练的重复点击，但要有撤销与审计 | 中 |
| 4 | 规则复发趋势 | 看同一条规则是不是反复亮，判断“偶发”还是“长期习惯问题” | 中 |
| 5 | 赛前 48 小时时间轴 | 价值最高、责任也最重；涉及脱水/补液，必须教练主导，不能自动开处方 | 大 |

**只做两个的建议**：先做 **官方称重对比 + 节奏红线看板**。两者都只读现有数据、都不改规则引擎、都不增加拳王填写负担；一个补齐数据闭环，一个直接提升教练的安全判断。48 小时时间轴留到有教练排班与订阅模板之后再上。

## 1. 节奏红线看板

**一句话结论**：把“每周掉多快、缺口多深、告警亮了几次”从每个拳王各自的日志里抽出来，做成教练能一眼扫完的总览。

### 解决什么问题

- 场景：营养师带 5–15 个拳王，每天逐个打开看日志；某个人连续两周每周掉 1.3% 体重，单日看都“正常”，只有把两周连起来才看得出风险。
- 现在没有它会怎样：`PHASE-01`（周降>1%）、`ENE-01`（缺口>900）、`HYD-01`（脱水）、`SLE-01`（睡眠不足）都只在当天日志里提示；教练要靠记忆和翻历史，容易漏掉“慢性越线”。
- 谁最需要：教练端。拳王端已经有单日结论和周报，不需要再做一个看板。

### 怎么做

**交互**

- 教练端新增“节奏”入口（可放在 `pages/coach` 顶部，或新开 `pages/rhythm`）。
- 每个拳王一行：最近 7 日/14 日体重速率、平均缺口、红灯/黄灯次数、最近一次记录日期、连续越线周数。
- 排序：连续越线 > 红灯 > 黄灯 > 数据不足；点一行进入该拳王周报/复核页。
- 时间窗切换 14/28 天；缺晨重或日志不连续时，明确标“数据不足”，不补 0、不猜。

**数据与接口**

- 不新建集合。历史日志里已经存了 `payload`（原始记录）和 `feedback.alerts`（含 `ruleId / level / evidence / reviewStatus`，见 `saveLog` 写库段）；`utils/weekly.js` 已能算 `weeklyRate / weeklyPct / sRPE`。
- 新增一个云函数动作（建议 `coachApi.getRhythmBoard`）：按 `coachOpenid` 取名下单人，拉最近 14/28 天日志，服务端聚合后返回每人一行，避免前端 N 次请求。
- 不改规则引擎：红线阈值仍由现有 18 条规则给出，看板只做汇总与排序。

**需要的新字段/集合/云函数**

- 新字段：无。
- 新集合：无。
- 新云函数动作：`getRhythmBoard`（读）。
- 建议顺带补一个写入字段：`logs.feedback.rulesVersion`，否则跨版本趋势不可比（见第 4 节）。

### 依赖

| 依赖 | 现状 | 是否阻塞 |
|---|---|---|
| 云端部署 `coachApi` | 已有，需确认正式环境 | 未部署则只能看本机缓存，不可用 |
| 拳王与教练绑定 | 已有 `users.coachOpenid` | 未绑定看不到数据 |
| 至少 14 天日志 + 晨重 | 取决于使用情况 | 新用户会大量“数据不足” |
| 历史告警已落库 | 已具备（`feedback.alerts`） | 无 |
| 规则复核状态 | 已具备 `reviewStatus` | 无 |

### 工作量：中

- 页面：1 个总览页 + 教练端入口（约 1 天量级）。
- 云函数：1 个聚合动作，含分页、权限校验（只能看自己名下拳王）。
- 测试：聚合口径、空数据、跨周对比、权限越界。
- 真机：列表滚动与数字刷新，弱网/分页。
- 主要成本在“聚合口径 + 权限”，不是页面。

### 风险

- **误报**：连续两次晨重波动就可能显示“越线”，需要标注“仅供参考、看趋势不看单日”。
- **数据拿不到**：拳王不填晨重时看板会大面积空白，容易让教练误以为“没问题”。
- **措辞风险**：“红线”容易吓人，建议 UI 用“需要关注/建议调整”，避免医疗诊断口吻。
- **隐私边界**：教练只能看已绑定拳王；聚合接口必须按 `coachOpenid` 过滤，不能靠前端传 athleteId。
- **查询成本**：人数×天数会放大读取量，需要限制窗口与分页。

## 2. 赛前 48 小时时间轴

**一句话结论**：把赛前最后两天的“什么时候吃什么、喝多少、记录什么”排成一条时间轴；默认只给教练编辑的框架，不自动生成脱水方案。

### 解决什么问题

- 场景：称重前 48 小时，拳王在群里反复问“今晚还能喝水吗”“最后一餐几点”；教练每次手动复制一段话，容易漏项，也不容易确认拳王照做。
- 现在没有它会怎样：`phase=peak` 的规则只给原则性提示（低纤维、低体积、按计划补液），没有按小时排的执行清单；`hydrationPlan`、`postWeighIn` 有字段但没有“时间轴”视图。
- 谁最需要：赛前拳王 + 教练；日常训练不需要。

### 怎么做

**交互**

- 触发条件：`goal.weighInDate` 存在且 `daysToWeigh ≤ 2`，或教练手动打开。
- 时间轴节点：T-48h、T-24h、T-12h、T-6h、称重当时、称重后 0–2h；每节点三行：“做什么 / 吃什么喝什么 / 记录什么”。
- 教练可编辑每个节点的文字与是否提醒；拳王只能查看与勾选“已完成”，不能改方案。
- 提醒走订阅消息；没有订阅授权时只在小程序内显示，不承诺推送。

**数据与接口**

- 计划来源：新增 `profile.preWeighPlan`（教练写的节点文本 + 开关，默认空），或复用 `profile.note` 不推荐（不可结构化）。
- 时间轴生成：新增纯函数 `utils/preWeigh.js`，输入 `weighInDate / phase / hydrationPlan / postWeighIn / now`，输出节点列表；**不要放进 `rules.js`**，避免破坏“无目标严格 no-op”。
- 写入：`coachApi.setPreWeighPlan`（教练唯一写入方）；拳王端只写“完成勾选”（可存在 `logs.preWeighCheckins` 或本机缓存，建议先本机）。
- 提醒：新增订阅场景 `preWeigh`，模板 ID 由 `whoami` 环境变量下发；现有场景只有 `coachLog / athleteMsg / advicePublish / adviceChange`。
- 规则引擎：不改 18 条规则；HYD/GI 原则仍由现有规则输出，时间轴只是执行层。

**需要的新字段/集合/云函数**

- 新字段：`profile.preWeighPlan`（可选）；`logs.preWeighCheckins`（可选，或先本机）。
- 新集合：无。
- 新云函数动作：`setPreWeighPlan`（写）、`getPreWeighTimeline`（读，可由 `getFeed` 复用）。
- 新订阅场景：`preWeigh`（需在微信后台申请模板）。

### 依赖

| 依赖 | 现状 | 是否阻塞 |
|---|---|---|
| 称重日可读 | `goal.weighInDate` 已有 | 未填则无法触发 |
| 教练可编辑计划 | 需要新页面/新动作 | 阻塞 |
| 订阅消息模板 | 机制已有，`preWeigh` 场景未申请 | 阻塞“提醒”，不阻塞页面 |
| 教练赛前在线 | 运营前提 | 教练不在线时只能给默认框架 |
| 合规文案 | 需要法务/教练确认 | 涉及脱水与补液，必须先定边界 |

### 工作量：大

- 页面：时间轴 + 教练编辑态 + 拳王勾选态（约 2–3 个页面状态）。
- 云函数：读写两个动作 + 权限。
- 通知：模板申请、环境变量、发送与失败降级。
- 测试：时间边界（T-48/T-24 跨天、时区）、缺称重日、订阅未授权、教练/拳王权限。
- 真机：提醒到达率、弱网、跨天。
- 主要成本在“合规边界 + 通知链路”，不是画时间轴。

### 风险

- **责任风险**：脱水、钠负荷、补液量属于高风险操作；产品只能给“教练确认过的计划”，不能自动生成处方。
- **证据不足**：赛前 48 小时的精确小时级方案缺乏统一文献共识，只能按队内惯例与教练经验。
- **数据拿不到**：称重日不准、`hydrationPlan` 不填，时间轴会空转。
- **填写负担**：如果要求拳王逐节点勾选，赛前反而增加压力；建议默认只显示、可选勾选。
- **隐私**：赛前体重、补水方案属敏感信息，只对本人与绑定教练可见。

## 3. 规则复发趋势

**一句话结论**：判断同一条规则是“偶尔亮一次”还是“连续几周反复亮”，用来区分偶发波动和长期习惯问题。

### 解决什么问题

- 场景：某拳王 `SLE-01` 一个月亮了 12 次；教练每次只看到当天“睡眠不足”，不知道这是长期问题。
- 现在没有它会怎样：待办队列是“当天要处理的事”，没有“这条规则最近 30 天亮了几次”的视图；教练只能凭印象。
- 谁最需要：教练做周复盘；拳王端最多看“最近反复出现”的温和提示。

### 怎么做

**交互**

- 在教练端拳王详情或 `pages/rules` 增加“近 4 周/8 周规则复发”列表：规则名、亮灯天数、占比、连续周数、最近一次。
- 点一条展开：哪些日期、当时等级、证据、是否已复核。
- 只做“次数与趋势”，不做预测、不做排名羞辱。

**数据与接口**

- 不新建集合：`saveLog` 已经把 `feedback.alerts` 的 `ruleId / level / evidence / reviewStatus` 存进日志；按 `athleteId + date` 范围读取即可。
- 聚合放云函数（建议 `coachApi.getRuleTrend`），避免前端拉大量日志。
- **必须标注版本**：建议在 `saveLog` 的 `feedback` 里补 `rulesVersion`；历史日志没有该字段时标“旧版本，不可与当前版本直接比较”。
- 规则引擎不改：只读已落库的判定结果。

**需要的新字段/集合/云函数**

- 新字段：`logs.feedback.rulesVersion`（建议，写入端一处）。
- 新集合：无。
- 新云函数动作：`getRuleTrend`（读）。

### 依赖

| 依赖 | 现状 | 是否阻塞 |
|---|---|---|
| 历史告警落库 | 已具备 | 无 |
| 至少 4 周日志 | 取决于使用情况 | 新用户只有空表 |
| `rulesVersion` 标注 | 未存 | 不阻塞，但跨版本趋势不可信 |
| 规则复核状态 | 已具备 | 无 |

### 工作量：中

- 页面：1 个趋势列表 + 展开明细（可复用 `pages/rules` 样式）。
- 云函数：1 个聚合动作 + 分页。
- 测试：口径（天数 vs 次数）、连续周、旧版本数据、空数据。
- 真机：长列表与展开。
- 主要成本在“口径定义 + 版本可比性”。

### 风险

- **规则版本变化**：阈值一改，历史次数就不可比；必须按 `rulesVersion` 分组展示。
- **缺日志**：没记录的日子不等于“没亮”，只能算“按已记录天数”。
- **小样本**：4 周只有 10 天记录时，比例会失真，需标“样本不足”。
- **告警疲劳**：把次数做得很显眼，可能让教练过度干预；建议只做周复盘入口。
- **隐私**：趋势只对绑定教练开放。

## 4. 教练端批量待办

**一句话结论**：让教练一次勾选多条待办并统一确认/延后，减少重复点击；必须有撤销与操作记录。

### 解决什么问题

- 场景：一天 8 个拳王、20 条待办，教练要逐条点“确认”并填提醒语，重复且容易漏。
- 现在没有它会怎样：`pages/queue` 只能逐条 `confirm / snooze / unsnooze`；`followups`、`reminders` 已按条存在，缺少批量入口。
- 谁最需要：带人多、待办量大的教练。

### 怎么做

**交互**

- 队列页增加“多选模式”：按拳王/日期/规则筛选；勾选后底部出现“批量确认 / 批量延后 / 批量忽略”。
- 批量确认时提醒语默认沿用模板，可统一填一条，也可保持各自原文。
- 操作后 10 秒内可“撤销”；撤销以服务端记录为准，不靠前端记忆。

**数据与接口**

- 复用 `followups`（待办）与 `reminders`（提醒）集合，不改结构。
- 新增云函数动作：`coachApi.batchFollowUps`，入参 `{ action, itemIds[], reminderText?, days? }`；服务端逐条校验归属（`nutritionistId=OPENID`），返回每条结果，**部分失败不回滚已成功项**，前端逐条标状态。
- 幂等：已确认的条目再次提交直接返回 `already_done`，不重复写提醒。
- 规则引擎不改。

**需要的新字段/集合/云函数**

- 新字段：无（`followups` 已有 `status / nutritionistNote / reminderText / createdAt` 等）；建议补 `batchId` 审计字段。
- 新集合：无。
- 新云函数动作：`batchFollowUps`（写）。
- 建议补审计字段：`followups.batchId`（同一次批量操作的标记），便于撤销与追责。

### 依赖

| 依赖 | 现状 | 是否阻塞 |
|---|---|---|
| `coachApi` 已部署 | 已有 | 未部署时只能本机模拟 |
| `followups / reminders` | 已有 | 无 |
| 教练身份校验 | 已有 `coachOpenid` | 无 |
| 撤销机制 | 需要新做 | 批量越大越需要 |

### 工作量：中

- 页面：多选态 + 批量操作栏 + 撤销提示。
- 云函数：1 个批量动作，逐条权限校验与幂等。
- 测试：部分失败、重复提交、越权、撤销。
- 真机：多选交互与列表回滚。
- 主要成本在“幂等 + 撤销 + 审计”，不是按钮本身。

### 风险

- **误操作**：批量确认/忽略影响面大，没有撤销会很糟；必须二次确认 + 可撤销。
- **通知风暴**：批量确认会一次生成多条提醒，可能打扰拳王；需要合并或限流。
- **权限**：必须逐条校验归属，不能只校验一次。
- **审计**：批量操作要能追溯到人、时间与批次。
- **产品反效果**：批量处理会让教练更快但更粗；建议只允许“延后/忽略”批量，“确认”仍可要求逐条看提醒语。

## 5. 官方称重对比

**一句话结论**：把官方称重、当天晨重、目标体重放在一起，讲清“差多少、差的是什么、称重后怎么恢复”；数据模型已有，只差录入与展示。

### 解决什么问题

- 场景：赛前官方称重 54.0 kg，当天晨重 54.6 kg；拳王以为“还差 0.6 kg 脂肪”，其实多半是水分与胃肠内容物，称重后需要补液补糖。
- 现在没有它会怎样：`weights.official` 在契约与规则里存在，`postWeighIn.weighInKg` 也有，但 `pages/log` 没有官方称重输入；教练端也没有“官方 vs 晨重 vs 目标”的对比卡。
- 谁最需要：赛前拳王、教练复核。

### 怎么做

**交互**

- 录入：在赛前/称重日的填写页或复核页增加“官方称重 kg”一项（只允许 0.1 kg 精度）；已填则显示“官方称重：54.0 kg”。
- 对比卡：官方称重 vs 当天晨重 vs 目标体重；差值（kg 与 %）；近 7 日晨重均值；称重后 `postWeighIn` 的补液/碳水完成情况。
- 文案：明确“差值主要是水分与胃肠内容物，不等于脂肪”；称重后 0–2 小时关注补液与碳水，不鼓励继续减重。
- 没有晨重或没有目标时，只显示能算的部分，缺项标“数据不足”。

**数据与接口**

- 复用 `logs.weights.official`、`logs.postWeighIn.weighInKg`、`goal.targetWeightKg`、7 日晨重均值。
- 需要补：录入入口与 `normalizeLog()` 已接收 `weights.official`（规则里已在读，无需改引擎）。
- 规则引擎：不改；`postWeighIn` 相关规则继续按原阈值。
- 云函数：读接口用现有 `getFeed` / 日志详情即可，不需要新动作；若教练端要跨人对比，可在教练详情页拼装。

**需要的新字段/集合/云函数**

- 新字段：无（契约里已有 `weights.official`）。
- 新集合：无。
- 新云函数动作：无（读现有日志）；若要做“全队官方称重对比”，再加一个只读聚合动作。

### 依赖

| 依赖 | 现状 | 是否阻塞 |
|---|---|---|
| `weights.official` 契约 | 已有 | 无 |
| `normalizeLog()` 接收 | 已有（规则已读） | 无 |
| 填写页录入 | 没有 | 阻塞（本功能的主要工作） |
| 称重日/目标 | `goal.weighInDate / targetWeightKg` | 未填则只能显示官方与晨重 |
| 历史晨重 | 已有 | 无 |

### 工作量：小

- 页面：录入一项 + 一张对比卡（填写页/复核页二选一，建议复核页）。
- 云函数：无。
- 测试：只填官方、缺晨重、缺目标、官方 vs 晨重差值、称重后补液状态。
- 真机：数字输入与小数精度。
- 主要成本在“录入放哪、文案怎么说”，不在计算。

### 风险

- **误读**：把急性体重差当成脂肪，可能诱导赛后继续减重；文案必须写清“水分/内容物”。
- **秤不一致**：官方秤与家中秤误差 0.2–0.5 kg，需标注“不同秤不可直接比”。
- **隐私**：官方称重是敏感数据，只对本人与绑定教练可见；教练端不要展示给其他拳王。
- **缺基线**：没有当天晨重时，差值没有意义，只能显示官方与目标。

---

## 推荐排序与“只做两个”

### 排序

1. **官方称重对比**（小）：现有数据模型与规则都已支持，只差一个录入与一张卡；风险低、见效快，还能把“赛后继续减重”的误读挡住。
2. **节奏红线看板**（中）：安全价值最高。历史告警与周速率都已落库，新增的只是聚合与展示，不改规则引擎。
3. **教练端批量待办**（中）：效率收益明确，但必须先把幂等、撤销、审计做对；可以等看板上线后再做。
4. **规则复发趋势**（中）：洞察型功能，依赖至少 4 周数据与 `rulesVersion` 标注；没有版本标注时结论会失真。
5. **赛前 48 小时时间轴**（大）：价值最高但责任最重，涉及脱水/补液、订阅模板与教练赛前在线；等教练流程与合规定稿后再上。

### 如果只做两个：官方称重对比 + 节奏红线看板

理由：

1. **都不增加拳王填写负担**：一个只加一项称重录入，一个完全只读；不会让日常记录变重。
2. **都不动规则引擎与矩阵**：现有 18 条规则、15/16 原子矩阵保持冻结，避免“功能上线顺带改判定”。
3. **都建立在已有数据上**：`weights.official` 与 `feedback.alerts / weeklyRate` 已经存在，不需要新集合、不需要补历史。
4. **一个补闭环、一个提安全**：官方称重对比让赛前数据能被正确解读；红线看板让教练从“逐人翻日志”变成“先看谁需要关注”。
5. **风险可控**：两者都不涉及自动处方与订阅推送；隐私边界仍是“绑定教练可见”，没有扩大。

**暂缓的理由**：48 小时时间轴不是技术难，而是责任与合规难；批量待办不是不能做，而是没有撤销/审计前容易出事故；复发趋势要先补 `rulesVersion` 才可信。
